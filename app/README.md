# Демо «Линия 1: прогноз нагрузки» (локально)

Интерфейс диспетчера + эмулятор, который проигрывает **реальные рабочие дни** из данных турникетов (15 минут).
Для дня месяца M используется модель, **не видевшая месяц M при обучении** (честный прогноз вне выборки).

## Запуск
```bash
pip install -r app/requirements.txt
python -m uvicorn app.server:app --port 8000      # из корня репозитория
```
Открыть http://localhost:8000 (старый интерфейс: `/classic`). Модели лежат в `app/models/`, переобучить: `python app/train_models.py && python app/train_ensemble.py`.
Chronos-2 скачивается с HuggingFace при первом запуске (нужна видеокарта; `METRO_CHRONOS=0` — без него, ансамбль из 4 моделей).
Данные берутся из `data/processed_15min_line1.parquet` и `data/weather_spb_2026.parquet`.

## Что показывает
- Карта линии: загрузка перегонов по двум направлениям (прогноз на ближайший час), отклонение станций от нормы (порог 20%).
- Одно главное действие: сколько составов добавить или что делать, откуда из депо, когда дать команду, почему.
- График входа по линии: факт, прогноз, норма.
- Станция по клику: прогноз по направлениям и причины.

## Эмулятор (панель сверху, клавиша E скрывает)
Главный сценарий — **«День события (модель)»**: реальная суббота 12.09, к входу четырёх северных станций (Площадь Мужества — Гражданский проспект) добавлен нарастающий приток: с 12:30 рост 45 минут до +240%, держится до 15:00, спадает 45 минут. Нажать ▶ и смотреть; около 13:15 появляется рекомендация.
Остальные сценарии: «сбой на другой линии» (модель, +45% утром по всей линии), реальные дни (13.02 утренний пик, обычный вечер, суббота, праздник); в списке справа — любой день из данных. «↺ Сначала» возвращает сценарий к началу.

## Диспетчер в эмуляторе
- Рекомендация выдаётся **в секундах интервала**: «сейчас 189 с → 168 с (−21 с)», ниже — сколько составов и из какого депо выпускать (Северное: 5 мин готовность + 8 мин ход, Автово: 5 + 7, плюс 2,6 мин на перегон).
- Поле «Текущий интервал»: по умолчанию график; можно задать вручную (например, диспетчер уже сократил интервал под известное мероприятие) — рекомендации считаются от него.
- Арифметика: интервал = оборот / составы на линии, оборот = 53 × 113 с ≈ 99,8 мин (сходится с «Графиком оборота составов»: 32 пары = 53 состава, 20 = 33, 15 = 25). Нужно составов = ⌈оборот / нужный интервал⌉, нужный интервал = 3600 / (нагрузка перегона / (0,85 × 960)); не больше 53.
- Горячий резерв — 4 состава, по 2 в депо «Северное» и «Автово». Сначала выпускается ближнее к участку депо, затем дальнее (выходит в обратном направлении и разворачивается на конечной). Если резерв выпущен, карточка «Резерв исчерпан» предлагает другие меры. Когда приток спадает (без добавленных составов загрузка на 2 часа ≤ 75%), система предлагает вернуть их в депо.
- «Принять»: составы добавляются с момента прибытия на участок и остаются на линии, пока их не вернут; в обратном направлении работают через полкруга (≈50 мин). Карта показывает загрузку «было → стало», график — «без принятого / с принятым». «Отменить принятое» возвращает как было; перемотка назад сбрасывает принятое.

## Как считается (коротко)
1. Прогноз входа по 19 станциям на 2 часа, рекурсивно, **ансамбль простым средним** (`app/ensemble.py`): LightGBM, LightGBM на остатке от нормы, MLP на отклонении от нормы, «инерция» последних 30 минут и Chronos-2 (без дообучения, норма как ковариата). Окно 05:30–00:15. Проверка «месяц в проверку»: WAPE ≈7,95% против 9,74% у нормы на тех же строках (без Chronos-2 ≈8,3%).
   Поправка «всплеск держится» (`decide.py`): модели обучены на обычных днях и тянут прогноз к норме; если станция за 30 минут выше нормы на 25% и больше (и это не меньше +150 чел., норма не меньше 100 чел.), прогноз на ближайший час не ниже текущего превышения плюс его рост за последние 30 минут (но не больше +35% к превышению), на второй час — 60% превышения.
2. Норма: медиана последних 4 таких же дней недели (запасная — из других месяцев), умноженная на уровень текущей недели (отношение факта к норме за прошедшие дни недели и последние 7 суток, 0,5…1,8). Как база это даёт 9,64% вместо 9,82%; как признак модели — вредит, поэтому в модели не используется.
3. Нагрузка перегонов по направлениям: упрощённая модель корреспонденций (затухание по расстоянию, средняя поездка 6 перегонов), масштаб откалиброван так, что пик плана = 85% комфортной вместимости.
4. Решение: нагрузка прогноза ≥88% комфортной вместимости (120 чел/вагон) и ≥+8% к норме ⇒ добавить поезда; если интервал уже на пределе (113 с), система говорит об этом и предлагает другие меры. Резерв: 5 мин готовность + 7–8 мин ход + перегоны.
5. Допущения (вместимость, средняя поездка, калибровка пика) нужно подтвердить у метро.

## Поминутный режим, поезда и проверка (10.10.2026)
- **Поминутный поток (модель, `app/minutes.py`):** 15-минутные суммы раскладываются по минутам (сумма слота сохраняется); каждую минуту модели получают скользящую сумму за последние 15 минут. Скорость эмулятора — минут в секунду (1/2/5/15).
- **Поезда (симуляция, `app/trains.py`):** отправления с конечных по интервалу; на каждой станции посадка = вход с прошлого поезда, высадка — по модели поездок. На карте — точки поездов, цвет = загрузка; под картой — сколько поездов в пути и на разворотах.
- **Резерв в два уровня:** горячий (4 состава, 2 + 2) и стоящие в депо между пиками (до 53 минус те, что на линии по графику; ≈30 мин на вывод — уточнить у эксперта).
- **«Составы в пути»** (жёлтая карточка): после «Принять», если загрузки хватит после прибытия принятых составов. Красная — только если не хватит и после.
- **Линия «прогноз, сделанный за час»** на графике входа и ошибка этого прогноза.
- Проверки: `analysis/demo_check.py` (прогноз против факта на демо-дне), `analysis/recs_stats.py` (рекомендации на 120 реальных днях), `analysis/plot_algorithm_charts.py` (графики для защиты).
